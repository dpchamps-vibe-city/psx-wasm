# M13 — Breath of Fire IV: a game with no decompiled C

**Status:** in progress (the headless replay reaches the first field
scene and walks in four directions, with every check passing; the
harness push and so a GitHub-installable pin wait on the human)
**Depends on:** M2, M8. Parallel with M7. **Unlocks:** M9's generality
claim, on a game whose code is entirely translated.
**Design refs:** design §3 (overlays), §4 (one implementation per
function), §5 (the SDK boundary), §6 (time, interrupts and blocking);
decisions D2, D4, D40–D48.

## Goal

**End result:** headless runs that play Breath of Fire IV (SLUS-01324) from
power-on to the first controllable field scene, deterministically, with no
traps. Every game function is translated from the original MIPS, because
bof4-decomp has no decompiled C yet.

This shows that psx-wasm recompiles an arbitrary PsyQ game, not only one
whose decomp did most of the work.

## Three repositories

The work spans three repositories, in this order.

| Repo | Role | Where |
|---|---|---|
| **psx-decompilation-harness** | Shared decomp tooling: splat config generation, overlay discovery (now EMI), SDK conversion and placement, the byte-identical build check | `../psx-decompilation-harness` (remote `software-factory-vibe-city/psx-decompilation-harness`). Projects install it with pi into `.pi/git/github.com/software-factory-vibe-city/psx-decompilation-harness`. |
| **bof4-decomp** | The decomp. Its configs are generated by the harness and committed. | `../bof4-decomp` |
| **psx-wasm** | This repo. It reads bof4-decomp only through a pinned commit (`inputs.lock`). | here |

**Rules across the three**
- **Each change happens in its own repo and is committed there.**
  - Harness fixes go in `../psx-decompilation-harness`, never in a
    project's `.pi/git/…` copy.
  - bof4-decomp pins the harness commit it was generated with.
  - psx-wasm pins the bof4-decomp commit.
- **Generality applies everywhere.** No harness code is specific to
  bof4, and no psx-wasm Rust code is (conventions: Generality). Game facts
  go in `games/bof4/game.toml` or in bof4-decomp's configs.
- **Pushing harness commits to GitHub publishes them.** That needs the
  human's go-ahead. bof4-decomp installs the harness from GitHub, so it
  can't pin a commit that hasn't been pushed.

## Context (measured 2026-10-28/29)

**The disc and the EXE**
- SLUS-01324: two tracks, pinned by sha1 in `inputs.lock`.
- The EXE loads at `0x800F8800`–`0x801F9000`.
  - `.text` runs from `0x80139598` to `0x80172BE4`.
  - The entry point `0x801395A0` is in SN's startup (`2mbyte`).
  - gp is `0x8017C524`.
- SYSTEM.CNF: `TCB=4`, `EVENT=16`, `STACK=0x801FFF00`.

**Overlays**
- 1,004 `.EMI` archives hold 9,857 components. EMI is a sector-framed
  container whose descriptor gives each component's load address.
- The harness's new EMI adapter (`discover-overlays`) yields 640 overlay
  configs, which load into 8 slots:
  `0x801F0800`, `0x801E6800`, `0x801EE800`, `0x801F8800`, `0x801AA000`,
  `0x801CC800`, `0x800F8800` and `0x8018D800`.
- The `0x800F8800` slot overlays EXE rodata.
- Within a slot, distinct bodies have distinct first two words, so
  residency by the bytes in RAM works (design §3).

**The harness's uncommitted state.** Both working trees are at `86749e4`,
with the bof4 bootstrap's work uncommitted.
- **`../psx-decompilation-harness`** (58 changed or new files):
  - the bof4 source changes: EMI (`tools/lib/emi.ts`,
    `tools/build/discoverOverlays.ts`, `deduplicateOverlays.ts`,
    `overlayCanonical.ts`), nullable leading pointer tables
    (`overlayBase.ts`), SDK placement (`detectLibFunctions.ts`,
    `patchSplatForLibs.ts`, `splitSdkLibs.ts`, `sdkImageBindings.ts`,
    `sdkPlacementPath.ts`) and the parallel build (`parallelBuild.ts`,
    `pipelineWorker.ts`, …);
  - tests for them: `emi`, `overlayCanonical`, `linkerInputs`,
    `linkIncludes`, `generatedAsmIncludes`, `sdkImageBindings`,
    `patchSplatForLibs`, and others.
- **bof4-decomp's `.pi/git/…` copy** (53 changed files) is the one bof4
  builds with.
  - It has the same source changes but none of the new tests.
  - It also has a change the other copy lacks: the old-gcc vendor pin moved
    from the unavailable `c8c4b40` to release `0.17` (`b74211c`), in
    `templates/vendor-sources.json` and `docs/migration.md`.
- **The pin.** bof4-decomp's `.pi/settings.json` names the harness without
  a ref. The harness README supports `…/psx-decompilation-harness@REF`.
  Without one, a fresh clone installs the default branch and regenerates
  different configs.

**Harness gaps, found by psx-wasm**
- **Overlays aren't scanned for SDK code.** SDK detection and placement
  (`detectLibFunctions.ts`, `patchSplatForLibs.ts`) read only the main EXE
  (`_info().binaryPath`).
  - btn has no SDK code in its overlays, so it never mattered.
  - bof4's movie player, `ovl_4414` (DEMO.EMI record 3, slot
    `0x801CC800`), links libpress (`libpress`, `vlc_c` and `build`:
    `DecDCTReset`, `DecDCTin`, `DecDCTvlc2`, …). It is split as plain
    `ovl_4414_func_…`.
- **Placement coverage isn't checked.** The byte-identical build passes
  whether an SDK object is placed or left as asm. 21 matched EXE objects
  (29 KB, including libgpu/sys and libpad/pdresres) stayed unplaced until
  psx-wasm's lift flagged them.
- **Nothing checks that generated configs are current.** `overlays.json`
  and the overlay configs were committed in `f2caee11` from a harness
  version older than the pointer-table fix. That broke five overlays until
  they were regenerated.

**The decomp** (bof4-decomp @ `48159a8`)
- A splat scaffold with no decompiled C: every function is `INCLUDE_ASM`.
- Every matched SDK object in the EXE is placed as `o` (PsyQ 4.7, as btn
  does), except `2mbyte`, which stays assembly on purpose.
- The overlay pointer tables are split correctly.

**What psx-wasm does with it today**
- **`psxw census bof4 --no-probe`:** PASS. 13,626 functions go to the lift
  tier.
- **`psxw lift bof4`:** all 14,809 functions in 641 containers translate
  and compile.
  - 904,612 instructions, 482 jump tables, 1,406 indirect calls, 59 BIOS
    call sites.
  - **1 problem:** `func_8013A308` (below).
- **`psxw build bof4`:** fails. `_patch_card` (libcard/patch) and
  `firstfile` (libapi/first) touch kernel RAM, are reachable, and have no
  validated adapter. The verdict can't be trusted yet, because:
  - `psxw identity bof4` finds **0** SDK members;
  - `crates/psxw-inputs/src/identity.rs:180` counts only `o` entries with
    no section as text, and bof4 writes `.text` explicitly.

**SDK objects that need a policy or validation**

| Library | In bof4 | Status |
|---|---|---|
| libapi | 6 objects | `counter`, `first`, `pad`, `patch` are in `validated.rs`; `chclrpad` and `padstop` aren't |
| libcard | 5 | `init` is validated; `card`, `end`, `format`, `patch` aren't |
| libcd | 18 placements | only `s_023` is validated |
| libds | 20 placements | no boundary entry; it falls back to `adapter`, and no adapters exist |
| libpress | 3 objects in `ovl_4414` | not placed until task 3 |
| libsn | `op_vnew`, `op_vdel` | SN-built; psyq-decomp excludes them; no boundary entry |
| 2mbyte | startup | assembly by design; no boundary entry |

The unvalidated objects aren't different from btn's. btn simply never
linked them, so no adapter was ever checked against them.

**The BIOS**
- bof4 calls 54 distinct BIOS functions. psx-bios has no entry for 5 of
  them:
  - `A0h:2Fh` rand;
  - `A0h:43h` Exec;
  - `B0h:0Eh` OpenThread, `B0h:0Fh` CloseThread and `B0h:10h`
    ChangeThread.
- **Threads:** `OpenThread` is called from `0x8013A40C`, `ChangeThread`
  from 4 sites and `CloseThread` from 3.
- **What `func_8013A308` does.** It reads the TCB array pointer at kernel
  address `0x110`. Then, for four threads:
  - it sets each TCB's saved status register (`+0x94`) to `0x40000404`,
    which enables COP2 (the GTE) inside the threads;
  - it fills a table at `0x80114800` (4 × 128 bytes) with each thread's
    TCB pointer and a 0x200-byte stack between `0x801FF600` and
    `0x801FFC00`.
- psx-bios keeps kernel state in Rust, not in guest RAM, so today that read
  of `0x110` finds nothing.

**Pointer-based I/O.** The lift detects I/O only at constant addresses.
PsyQ libraries (and possibly Capcom's code) reach registers through
pointers. Such an access from a function with no device routing doesn't
trap: it silently writes window RAM at the register's masked address.

**The disc reader.** `crates/psxw-host-native/src/disc.rs` already parses
multi-`FILE`/`TRACK` cues. Track 2 has not been exercised.

## Scope

**In**
- **Harness:** commit the bootstrap work; scan overlays for SDK code;
  check placement coverage; check that generated configs are current.
- **bof4-decomp:** pin the harness; regenerate; commit.
- **psx-wasm:**
  - generic fixes that make the build's verdict trustworthy;
  - BIOS threads (D57);
  - a CD route for libds and unvalidated libcd (D58);
  - an MDEC device;
  - validation of every SDK object bof4 links;
  - boot, then a scripted replay to the first field scene;
  - `psxw ci bof4`.

**Out**
- The browser host for bof4 (M5's criteria), difftest (no C to test yet),
  `ramdiff` equality (D48), saves, and a long play session. Those belong to
  M9 once this lands.
- Decompiling anything.

**Decisions (the human's; record in `decisions.md` and `docs/design.md`)**

11. [x] **D57: how guest threads run.** Recorded: (a), as recommended.
    - ChangeThread has to suspend one guest call stack and resume another.
      A translated function's MIPS registers live in wasm locals, so the
      wasm stack itself must be switched.
    - **Start by characterizing bof4's threads:** what each thread runs,
      where ChangeThread is called, and the stack depth there.
    - **Options:**
      - **(a) Asyncify (binaryen, already pinned).** Instrument only the
        functions that can be on the stack at a ChangeThread, computed
        from the call graph, with indirect calls resolved through the
        dispatch table. It works the same under wasmtime and in browsers
        and is deterministic. The cost is size and speed in the
        instrumented functions, which needs measuring.
      - **(b) Wasm stack switching (continuations).** The cleanest, but
        host support is uneven, and it would split the browser host.
      - **(c) One instance per thread over shared memory, with strict
        handoff.** This needs a shared-memory build and syncs per-instance
        globals on every switch; it's the heaviest.
    - **Recommendation:** (a), scoped by the call graph, after the
      characterization.
12. [x] **D58: the CD for libds and unvalidated libcd.** Recorded: (b),
    with `adapter-or-device` decided per library (see D58).
    - **(a) Ds adapters** over the existing drive model, plus conformance
      for each of bof4's 16 unvalidated libcd placements.
    - **(b) A register-level CD controller** (`0x1F801800`–`3`, IRQ2,
      DMA3), with libds and those libcd objects run as original code. This
      follows D40, D42, D45 and D47, and it is D48's first route.
    - **Recommendation:** (b), with a new boundary policy,
      `adapter-or-device`:
      - objects with a validated adapter keep it, so btn is unchanged;
      - every other object runs as original code over the device.

## Exit criteria (all automated)

1. **Harness:** at its pushed commit, `npm test` passes, and `check-all`
   includes the placement-coverage and configs-current checks.
2. **bof4-decomp:** at its pinned commit (harness pinned by ref),
   `npm run check-all` passes, including both new checks.
3. **psx-wasm builds it:** `inputs.lock` pins that bof4-decomp commit, and
   `psxw lift bof4` and `psxw build bof4` pass with no problems.
4. **The headless run:** `psxw run bof4 --replay title-to-field --check
   determinism --check no-trap --check no-shadow-io` passes, and every
   `expect` in the replay holds.
5. **Device oracles:** the CD controller (if D58 picks (b)), MDEC and
   thread checks pass. Their goldens are labelled provisional where they
   come from Beetle.
6. **CI:** `psxw ci bof4` passes from a clean checkout of the pinned
   inputs, and `psxw ci btn` still passes with btn's tiers unchanged unless
   a recorded decision says otherwise.
7. **Generality:**
   - No psx-wasm Rust code and no harness code mentions bof4 or a bof4
     address. A reviewer agent checks this.
   - Game facts live in `games/bof4/` and bof4-decomp's configs.

## Risks and decision points

- **Human calls:**
  - D57 and D58 are design changes: ask before implementing (README, rule
    6).
  - Pushing the harness is outward-facing: ask before pushing.
- **Two harness copies.** Until task 1 lands, the canonical checkout and
  bof4's `.pi/git/…` copy disagree, and the copy is what builds bof4.
  Reconcile before anyone makes more harness changes.
- **Size and speed.** 900k translated instructions, plus Asyncify if D57
  picks it, may make `game.wasm` large and slow to link. Measure at task
  16.
- **Hardware access hidden behind pointers** in Capcom's own code shows up
  only at run time. Task 9's check exists for that.
- **Lifted functions that read temporaries on entry** (follow-up-tasks
  "Gaps") will recur at this scale.
- **FMV and XA streaming** depend on CD timing. D48's caveats apply to any
  comparison with Beetle.
- **Track 2.** If it's CD audio, the CD needs a Play path and SPU CD
  input.

## Findings

- **A second pad changes bof4's path.** With a pad in port 2 (as every
  replay had) the game draws nothing and its loop runs at a fixed rate;
  with port 2 empty it plays normally. Whether hardware does the same is
  open; the replay format now records the pads plugged in, so a one-pad
  session is what's replayed, natively, in the browser and under Beetle.
- **Dead loads matter.** libcd's streaming interrupt drains 8 bytes of a
  sector header with loads whose results nothing reads; clang deleted
  them, so the FIFO fell behind and every movie sector was dropped.
- **Hand-written decompressors** use three idioms the GCC-shaped lift
  didn't handle (an in-text jump table, Duff's device into an unrolled
  copy reached by a stored code pointer, and returns through `ra` kept in
  another register); each is now handled generically (design §4).
- **The first field scene** is at counter about 12,300 (frame 24,600),
  after about 280 dialogue advances. Its controllable state shows in
  Nina's facing halfword (`D_80117334`), whose high byte is twice the
  direction plus one.

- **Device oracles (tasks 13–14), `0c3dd0d` and `9a8a9d2`.** Captured on
  Beetle + OpenBIOS and checked by `psxw oracle check <game> --device
  mdec|cdc|threads` (all provisional, none failed or unresolved):
  - `mdec_run`, 49 vectors (libpress's tables, every output depth, edge
    cases, isolating cases). The golden showed the IDCT's output
    transposed against the first implementation, and that 15-bit and
    4-bit output round (add half a step, saturate) instead of truncating.
  - `cd_cmds`, 14 vectors on a generated runner-disc file: status
    commands, seeks, ReadN/ReadS at both sizes and speeds. Interrupt
    types, response bytes and sector data compare exactly (2340-byte
    sectors by EDC too); times and the head position while not reading
    are recorded, not compared (D48). Test 20h answers `97 01 10 C2`, as
    the oracle's drive does. The interrupt enable reads 1Fh after boot, as
    the runtime now starts it.
  - `bios_threads`, 4 vectors: handles, TCB statuses and fields, what
    ChangeThread returns, a full table. OpenThread also writes 1000h into
    the TCB word after the status, as OpenBIOS does. OpenBIOS saves every
    register into a thread's TCB when it switches away; psx-bios saves only
    sp and gp, because the rest are wasm locals (D57), so a reused TCB is
    refilled by the vector before it is compared.
- **Harness tasks 2–4 on bof4** (before regeneration): placement coverage
  first flagged 105 matches; two rules made detection sound (an
  overlay's imports must agree with the EXE's verified SDK addresses, and
  an object made only of empty functions isn't a match: libsnd `vm_vib`
  in 21 overlays). What remained was libpress in ovl_4414 (now placed)
  and libsn `op_vnew` (deferred with `2mbyte` in
  `configs/deferred-sdk-objects.json`). Configs-current found
  `configs/overlays.json` stale for five members.

- **The split misses leaf functions at the start of overlays.** Calls
  from other containers land where the configs have rodata: `ovl_4319`'s
  code starts at `0x801E6808` (a `lui`/`lhu` pair scheduled before the
  `addiu sp` the splitter keys on), `ovl_5659` has a frameless setter at
  `0x800F886C` (`lui v0; jr ra; sw a0`) and `ovl_7271` a getter at
  `0x800F88E4`, all inside the leading region split as rodata. 19 call
  sites in 17 overlays reach them. That's a harness fix (cross-container
  call targets as code evidence) plus a regeneration, not a hand edit.
- **`adapter-or-device` can't be per object.** bof4's libcd has one
  validated adapter function (`CdDataCallback`), but its game code and
  libds call libcd's drive layer directly (`CD_cw`, `CD_init`, `St*`). A
  bound `CdDataCallback` adapter would keep the callback in the runtime,
  where libcd's original interrupt code never looks. The policy is
  decided for the whole library by what outside code reaches past the
  adapters (D58).
- **The BIOS leaves the CD controller's interrupts enabled.** libcd's
  `CD_init` writes the enable register only when flags are pending, so a
  controller that resets it to 0 never raises IRQ2.
- **Threads in practice.** bof4 runs a round-robin scheduler on the main
  thread over up to four worker threads, each yielding with
  `ChangeThread(0xFF000000)` from arbitrary depth. Asyncify over the
  reverse call graph plus every indirect caller covers 21% of functions
  and costs little: 600 frames run in 1.7 s headless.

- **The lift is a free split validator.** The lift's FAIL on 12 overlay
  functions was the split's fault (pointer tables split as code), not the
  translator's. A word like `801Fxxxx` decodes as `lb ra, xxxx(zero)`,
  which the kernel-access check caught.
- **psx-wasm saw mistakes the harness's byte check couldn't.** The lift's
  I/O check found the unplaced SDK objects, and the identity scan found
  libpress in an overlay. Byte-identical builds pass in both cases. Tasks
  3–4 move those checks into the harness, where they belong.
